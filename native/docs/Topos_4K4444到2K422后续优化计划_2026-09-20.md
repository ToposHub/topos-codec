# Topos 4K 4444→2K 422 后续优化计划

日期：2026-09-20

范围：Windows 本机、`tests/test_videos/4K_topos_4444.mov`、Topos 原生解码/直通导出链路。

关联提交：`870508ec`（固定 2:1 原生缩放坐标快路）。

## 1. 当前基线

当前链路已经是：

```text
4K 4444 Topos
  → native reduced/half decode（2K Y/U/V，跳过 Alpha）
  → native 4:4:4→4:2:2 平面转换
  → Topos 422 Proxy 编码
```

最近一次本机实测为 48 帧、暖机后、Zig Release DLL、16 个 native worker：

| 项目 | 当前结果 | 说明 |
| --- | ---: | --- |
| 4K 全分辨率 native 解码 | 76.4 FPS | 输出 3840×2160 三平面 |
| 4K→2K native 缩放解码 | 56.5 FPS | `mode=REDUCED`、`scale=HALF`，输出 1920×1080 三平面 |
| 4K 4444→2K 422 直通导出 | 23.2 FPS | 24 帧实际导出，输出 `yuv422p10le` |
| native 目标帧平面内存 | 约 12.4 MiB | 全 4K 三平面约 49.8 MiB，目标路径明显降低内存压力 |
| 正确性回归 | 971 passed | 全量相关 Python/native 绑定回归 |

当前结论：原生缩放路径已经正确接通，但缩放解码暂时没有比全分辨率解码更快。主要瓶颈不是 2:1 坐标除法，而是 V7 缩放分支的熵解码、系数重建和写平面开销；后续优化必须以分项 profile 为依据，不能直接扩大线程数或重新启用已验证退化的批量 IDCT。

## 2. 执行计划表

工期是单人有效工作日估算，不是收益承诺。每一项完成后都要记录 commit、DLL SHA、素材 SHA、命令、线程数、暖机策略和 p50/p95/p99；未通过验收的实验只保留在分支或实验开关中，不替换默认路径。

| --- | --- | --- | --- | --- | --- |
| T0 | P0 | 固定 2:1 native 坐标快路；覆盖右/下边缘、奇数保护、Alpha 丢弃、旧 DLL 回退；补 C golden 和真实 4K 4444→2K 422 集成回归 | 无 | 全量相关测试通过；输出尺寸、位深、色度、Alpha 语义不变；旧库仍可回退 | **已完成** |

## 3. 建议执行顺序

```text
T1 分项 profile
  ├─→ T2 专用 half-scale 重建
  │     └─→ T3 AVX2 / scalar 双路径
  ├─→ T5 pool 与复制优化
  └─→ T4 解码-编码流水线

T6 格式矩阵 ──→ T7 Windows 发布适配
T1/T4/T6 ────→ T8 性能回归门 ──→ T9 长稳测试
```

优先处理 T1，而不是直接继续改熵编码或盲目增加 worker。当前 4K 全分辨率已经约 76 FPS，说明“更多线程”未必能解决缩放路径问题；需要先确认时间究竟消耗在 token 解码、逆变换还是目标平面写入。

## 4. 每项优化的统一验证模板

1. **正确性**：新旧路径输出 Y/U/V/A 平面逐值对比；记录尺寸、stride、bit depth、range、matrix、transfer、primaries 和 Alpha 语义。
2. **性能**：至少 5 轮交替 A/B，丢弃首轮暖机；记录总 FPS、单帧 p50/p95/p99、首帧延迟和导出墙钟时间。
3. **资源**：记录 peak RSS、plane pool 条目、read-ahead 深度、worker budget、临时文件和取消后的资源回收。
4. **兼容**：分别用新 Zig DLL、旧 DLL 和无 native helper 的回退路径验证；diagnostics 必须标明实际 decode path。
5. **提交**：一项优化一个 commit，commit 信息包含 `T1`～`T9` ID；测试命令和实测结果追加到本计划表或对应报告，不覆盖历史结果。

## 5. 暂不投入的方向

| 方向 | 暂缓原因 |
| --- | --- |
| 直接重新启用 4-block batch IDCT | 之前受控 A/B 没有带来稳定收益，且 scaled path 的收益不能从 full path 推断 |
| 单纯扩大 read-ahead 或 native worker 数 | 可能增加内存和争抢；当前瓶颈尚未完成分项归因 |
| 先重写 VLC/Rice 位流 | 这是协议级变更，必须先证明熵解码占比达到门槛，并通过 bit-exact、坏包和跨 DLL 兼容测试 |
| 用 Python/NumPy 继续做全帧缩放 | 虽有时单次基准较快，但会增加 4K 源平面内存和复制，不符合原生缩放目标 |
| 直接宣称已达到实时导出 | 当前端到端约 23.2 FPS，距离稳定 25 FPS 仍需 T4/T5 优化和多轮验证 |
