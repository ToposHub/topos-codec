# Topos 深度审计与完整优化计划（2026-09-03）

## 0. 结论、范围与执行规则

**当前结论：Topos 已在特定静态、纯解码内核口径接近或超过 FFmpeg ProRes，4K 内核也超过该特定实现；但不能据现有证据宣称整体产品路径或编码质量/速度已追平 ProRes、DNxHR，更不能宣称超过它们。** 先修复基准与交付语义问题，重新取得可追溯证据；在此之前不接受新的“性能已经追平/超越”结论。

本轮只读深审对象是 `e99468ab`（2026-09-02），包括 native codec、Python 产品导出/读取路径、benchmark、质量和发布证据。构建一致性已复核：以该提交重新配置 Release 后，`ctest` **45/45 通过**；这不等于基准和发布门已通过。产品回归：`.venv/bin/python -m pytest -q tests/media/test_topos_source.py tests/media/test_topos_export.py tests/media/test_topos_timeline_export.py` **148 passed**。

### 当前可保留的历史观察（不得升级为发布结论）

| 层级 | 历史观察 | 解释 |
| --- | --- | --- |
| 静态纯内核解码 | 2K HQ 约为 ProRes 的 0.94；同码率档约 1.00；4K HQ/Standard 约 1.13–1.21 | 仅是特定静机、特定实现、不同输出契约的内核数字；不是应用端到端数字。 |
| 产品顺序解码 | 读前批量 + arena 后，2K 324→362.4 fps、4K 86.6→98.3 fps | 说明批量读取有效；没有同窗 ProRes 产品路径 A/B。 |
| 编码 | 单遍固定 QP 原生快于 `encode_sized`；最近 mux 改动的单项 A/B 为 +6.6% | 不可与另一脚本的 41–43 fps 合并；现有参考对照不公平。 |
| 质量 | 最新可见 4K 历史样本：Topos HQ 63.24 dB @ 767.4 Mbps，ProRes 66.58 dB @ 649.5 Mbps | Topos 码率仍高 18% 而 PSNR 低 3.34 dB；源还是 ProRes，不是无损参考。 |

### 共同规则

1. 每项优化先写 hypothesis、当前基线、优化上限、回滚条件；只接受**同一 clean HEAD、同一动态库 SHA、同一素材和同一线程策略**的交替 A/B 结果。
2. 分开报告 A=codec core、B=demux+decode、C=应用归一化帧/渲染导出。禁止跨层相除得到“领先”。
3. 任何结果写入不可覆盖目录：`bench_out/<commit>/<lib_sha>/<manifest_sha>/<utc>/`，manifest 记录 `tc_version()`、dylib SHA、git clean、编译 flags、CPU/OS、线程、素材 SHA、命令行和原始样本。
4. P0 未关闭前冻结性能宣称；P0/P1 每项必须有回归测试，所有 bitstream 改动必须 golden、截断、fuzz、旧解码器兼容性一起过。

### 阶段 B（P1，先守住实时性与资源）

1. **资源和调度：** P1-03/04/05/06/07/08。先加入 metrics（pool fallback、cache hit、decoder path、queue depth、RSS、线程配置来源），再决定 pool/context ABI；不能仅扩大 ring 或线程数。
2. **协议和产品契约：** P1-01/02/09/10/14。把音频策略、slice rows、V2 feature switch、SDK 固化成明确且可测试的用户契约。
3. **数据搬运：** P1-11/12/13。先 profile 三层耗时与 allocation；目标是 GPU/原生接口消除 Python 大平面临时对象，而不是在 NumPy 表达式上微调。

### 阶段 C（质量优先的编解码优化）

先完成 P2-01 的 RD 基线。质量不达标时，优先改善变换/量化/码控或在同码率使用 V2 的真实 RD 收益；不得为了 fps 降低质量目标。编码侧保持“首帧定标 + 单遍反馈”的已验证路线，新增 scene-cut/复杂度突变检测：当连续帧 byte error 超阈值或 QP hit bound 时，触发一次 bounded `encode_sized` 重新 seed；记录 re-seed 次数、码率偏差、质量和速度，避免无限迭代搜索。

### 阶段 D（熵解码专项：**仅在 profile 证明熵是瓶颈后执行**）

现有实现已经有 Rice 12-bit LUT、融合 color scan，以及 V2 canonical VLC 12-bit 一级 + 8-bit 二级表（`entropy/color_scan.h`、`entropy/vlc.h`）。因此不要无测量地重写或反复微调码表。

1. **先定位。** 将每 slice 的 bitreader refill、Rice/VLC fast/slow hit、DC/run/level token 数、escape、EOB、cache miss、entropy wall time 记到 caller-owned profile snapshot；用 perf/VTune/xctrace 的 cycles、branch-miss、L1D-miss 交叉验证。门：entropy 占 decode wall ≥25% 且目标平台/真实素材稳定复现，才进入下一步。
2. **不改比特流的快路。** 保持现有 64-bit cache 和“窗口不足不消费→慢路”的截断语义。把 hot token 路径中的 `refill + peek + table + skip` 合并为单一 inline helper；预取本 slice 三张冻结 table；只在 `bits < need` 时 refill。每一改动与 scalar/reference 做逐 bit 截断、MALFORMED/TRUNCATED 错误码、输出 hash 对拍。
3. **V2 table 的安全实现准则。** primary entry 编码 `{kind,length,symbol/secondary-row}`，长码使用二级表；在完整验证后一次性 skip，禁止先消费 12 bit 再发现不足。表只在一次初始化/只读发布后使用，不能在播放热路径建树或训练。所有读取严格基于 payload end，禁止靠 padding 越界读取。
4. **只有 RD/CPU 都失败后才考虑新语法。** 单纯 VLC 表微调已被否证。若真实 profile 指向 token 数而非 bitreader，新增**版本化 V3 `entropy_mode`**，而非改写 V1/V2：常见 `(run, level-category/sign)` 设计 `ACPAIR` 复合符号，EOB/DC 分表；escape 表示罕见 run/category，幅度和符号保留 Rice/补充位。使用 12–16-bit primary table，entry 连续编码 `{nbits,type,run,cat,escape}`，长码走 secondary table；64-bit reservoir 做安全 peek、完整验证后单次 consume，热循环无函数指针、原子或额外边界分支。slice 独立、byte-aligned、显式 codebook version，旧 decoder 返回 unsupported。先完成独立 oracle、基于真实素材而非合成图训练、fuzzer、golden，再写 SIMD/汇编。
5. **Acceptance。** 新熵模式必须在每个目标码率满足 P2-01 质量门，decode median 和 p95 不退化、坏包隔离语义不变、跨平台 bit-exact。否则保持 V1 Rice 默认。

### 阶段 E（SIMD/平台优化）

在 Stage D 的 profile 之后，分别做 x86 AVX2/AVX-512（若可用）和 ARM NEON。优先补 ARM inverse transform/量化的等效快路径，采用 runtime dispatch，scalar 为 oracle；按输入对齐/尺寸/位深分桶。每次只改一个 kernel，要求 bit-exact、ASan/UBSan、2K/4K真实素材 A/B，以及 ARM64、x86_64、MSVC 结果。不要将 x86 的正向 AVX2 结果外推到 Apple Silicon。
