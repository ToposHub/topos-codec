# Topos：不降低画质的压缩与编解码提速计划

日期：2026-09-07 更新。状态：**第一批解码快路、分项计时、V3 worker-slot scratch、D1 播放源层审计、D2 V2 坐标快路、D3 context worker 预算、C0 符号预算、C1/C2 独立实验位流、E1 编码热点画像、Q0 软件对照首轮和 ASan/UBSan 异常输入门已实施；C1/C2 正确性通过但压缩/速度门失败，GPU 播放链与达芬奇公平实测仍未完成。**

实施进度记录见：[解码提速第一阶段报告](decode_speed_phase1_report_2026-09-06.md)。当前已落地 V3 融合 inverse、DC-only 快路、worker-slot scratch 池、分项计时修正、D1 播放源层基准、D2 V2 direct-scan 坐标快路、D3 共享 context worker 预算、C0 按平面 token 预算统计和 C1/C2 实际位流 A/B；默认 Topos 播放关闭同步 read-ahead，压缩语法与默认质量档位尚未改变。

## 1. 执行结论

下一步优先顺序为：**校准测量 → 加速现有默认播放链 → 对相同量化系数做更紧凑的无损表示 → 验证整条播放链 → 决定方向预测是否继续投入。**

“不牺牲画质”采用最严格且可自动验收的定义：新旧方案解码后的有效像素逐值相同，包括所有颜色平面和 Alpha，位深、色彩范围及解释元数据相同。这条路线不靠提高 QP、降低色度精度或去掉纹理来省空间。它保证的是**相对当前编码结果不增加损失**；当前有损档位不会因此成为对源图像数学无损。

“不牺牲解码速度”要求新方案的纯解码和产品播放延迟都通过不退化门。可以先靠实现优化获得速度余量，再在余量内引入压缩工具，但必须测试最终组合，不能用不同实验的百分比相加。无法保证任意输入都更小且更快；达不到门槛的候选继续保留为实验，不替换默认。

按用户要求，**旧项目兼容性不作为约束**。允许更改 ABI 和位流；仍需明确版本、能力查询与非法输入边界，避免新旧库误读。保留旧实现作为 A/B 和正确性参照，不要求为历史项目维护完整兼容产品链。

## 2. 当前事实与不能直接采用的推断

| 核查项 | 当前证据 | 对下一步的影响 |
| --- | --- | --- |
| 图片与视频共用内核，视频仍为全帧内 | `codec.c`；没有已实现的运动补偿链 | 内核改进可同时受益；视频不因有尺寸搜索就消除压缩效率限制 |
| V3 方向预测已实现但收益不足 | 两帧实拍相对 V2、AQ/RDO 关闭：同 QP 包体积约减少 0.1%～1%，Y-PSNR 略升，编码慢约 9～13 倍 | 不是严格同画质结果，不支持此前 20%～35% 收益预期；V3 不进入默认路线 |
| 当前图片默认策略与上述 V2 实验基线不同 | 图片 CLI 使用 V2 + AQ/RDO；原实验为隔离预测关闭两者 | 正式基线必须分别冻结图片六档、视频六档的实际配置，禁止选弱基线放大收益 |
| V3 分项计时失真 | V3 未更新 `sampled_ns/sample_blocks`，帧统计却据此扣除逆变换时间 | 重建时间会落入 entropy 项；先修计时，不能直接判定熵解码占比 |
| 产品链已有大量优化 | 持久 context、plane pool、原生读包、读前预算、批量解码、arena；原生已有线程池、融合写平面、AVX2 等 | 首先检查实际播放有没有启用及在哪里回退，不重复建设 |
| 平台差异明确存在 | x86 有 AVX2 inverse/dequant；NEON 分发当前只注册 forward | ARM inverse 是明确缺口，但不能用 ARM 工作解释本次 Intel 机器的差距 |
| 历史速度表不一致 | 8 月 31 日与 9 月 3 日报告采用不同版本/实现/输出契约；部分内核测试已接近或快于 FFmpeg 对照 | 历史结果只供定位；既不能证明当前慢多少，也不能证明达芬奇已被追平 |

证据：[第一阶段报告](intra_phase1_report.md)、[原始结果](intra_phase1_results.json)、[9 月 3 日深度审计](Topos_深度审计与完整优化计划_2026-09-03.md)、[既有码率优化记录](Topos_码率效率优化计划_2026-09-03.md)。后两篇包含不同日期的阶段决策；本文以当前代码和用户最新要求为准。

## 3. 验收标准：先把“不牺牲”变成机器能检查的条件

| 维度 | 必须记录 | 默认替换的门槛 |
| --- | --- | --- |
| 相对当前画质 | 有效像素逐值比较、逐平面 hash；Alpha、range、matrix、transfer、primaries、chroma 解释 | 所有有效像素完全相同，解释元数据相同；不能只比较总 PSNR |
| 对原始素材的质量 | Y/U/V 或 G/B/R 分开算 PSNR、SSIM、最大误差；HDR、暗部、颗粒、边缘；1/3/5/10 代 | 熵/实现优化必须与冻结基线一致；改变预测或量化的实验另列，不以平均 PSNR 上升冒充完全无损 |
| 总体积 | 完整 `.toos`/MOV 文件、包、各平面、模式、码表、padding、索引开销 | 验证集总字节数下降，逐文件不增长；候选选择与回退的信令开销也算入。做不到则不全量替换 |
| 解码时间 | core 和产品链各自的 p50/p95/p99；吞吐与首次出帧延迟分开 | 最终候选相对冻结基线的配对耗时比，其 95% CI 上界 ≤1.00；按平台/格式/场景分别判断，不用全局平均掩盖退化 |
| 编码时间 | 固定质量单次、sized 完整搜索、应用导出分别计时；记录探测次数 | 默认方案同样不退化；慢速候选不能借“只要求解码快”进入默认导出 |
| 交互及资源 | 顺序播放掉帧、随机 seek p95/p99、取消耗时、峰值 RSS、分配、队列深度 | 不倒退、不越内存预算；无新后台争抢、缓冲生命周期错误和隐藏串行回退 |
| 正确性 | scalar/SIMD/context/batch 对照；golden、截断、畸形流、fuzz、ASan/UBSan；并发修改加 TSan | 无像素漂移、越界、数据竞争；正常基准不能靠 concealment 成功 |

统计无法区分胜负时写“尚无结论”，延长配对实验或保留现状，不将 ±2% 噪声自动算作“不退化”。同一输入完全相同的像素哈希是强证据，但仍需覆盖格式与异常路径，不能仅验证两张图片。

**尺寸搜索须单独处理：**严格压缩实验固定基线逐帧实际 QP、量化系数及 AQ/RDO 决策。新熵表示变小后，若让 `encode_sized` 按新包大小重新选择最小命中 QP，可能选到更低 QP，像素随之改变；这属于“固定预算重新分配质量”实验，不能混入逐像素一致结果，也不能仅凭 QP 更低就免做逐平面质量验证。严格路线接入 sized 产品时，必须保留基线质量决策策略并计入实现成本；若改为新预算搜索，应明确作为另一种策略，不能同时宣称原搜索契约不变且输出逐像素相同。

## 4. 与 ProRes / DNxHR / 达芬奇怎么比

建立两个独立记分牌：**相同软件条件下的编解码实现对比**，以及**Topos 应用与达芬奇的实际播放体验对比**。FFmpeg 的 ProRes/DNxHR 数据不能标成“达芬奇解码速度”。

| 层级 | 测量边界 | 公平条件与输出 |
| --- | --- | --- |
| A：CPU 纯解码 | 预加载 packet → 输出原生平面 | 持久 context、复用输出、相同线程预算；明确双方分配/ownership，格式不一致的结果分表；不含磁盘与 GPU |
| B：产品取帧 | demux/read → 解码 → 应用可持有的帧 | 相同文件缓存条件、相同输出位深/布局及生命周期；包含必要拷贝；冷启动与稳态分开 |
| C：完整播放 | 请求帧 → CPU 平面 → GPU 上传/色彩/合成 → present | 全分辨率、无调色/特效的基础场景先测；再测实际调色、多轨、播放并行导出；记录关键路径，不能把并行 worker 时间相加当帧延迟 |
| D：达芬奇黑盒 | 实际时间线播放、seek、掉帧和最大稳定多流数 | 固定 Resolve 版本/Free 或 Studio、OS、CPU/GPU、存储、素材；关闭 Render Cache、Optimized Media、Proxy 和降分辨率播放；明确实际解码后端，无法观测就标未知 |
| E：编码 | 原生平面 → packet；另测原始输入 → 完整文件 | `prores_ks`/FFmpeg DNxHR 是软件编码器对照；达芬奇导出另测，包含转换、mux、I/O 和最终落盘 |

单路 25 fps 流畅播放只能证明赶上 40 ms 的帧截止时间，不能推导解码是 1 ms 还是 20 ms。达芬奇无法提供内核计时的部分，用帧截止时间、掉帧、首帧、seek 和饱和多流能力比较，不能编造“达芬奇纯解码 ms”。

ProRes 官方资料明确提供多核处理与降分辨率解码能力，因此必须核对实际播放分辨率。[Apple：About Apple ProRes](https://support.apple.com/en-us/102207)。Resolve 支持能力按系统列出；支持列表不是速度报告，也不能据此推定所有 ProRes/DNxHR 都走硬件解码。[Blackmagic：Resolve 20 支持格式与编码列表](https://documents.blackmagicdesign.com/SupportNotes/DaVinci_Resolve_20_Supported_Codec_List.pdf)。实际安装若不是 20，执行时使用对应版本资料；本计划尚未测量达芬奇。

### 基准素材与运行要求

- 冒烟集：每类 2 段，1080p/4K、422/444/GBR、10/12-bit、Alpha、奇尺寸；避免全部为静帧。
- 正式集：至少 12 个独立场景，每段至少 300 帧；覆盖实拍颗粒、细纹理、肤色、暗部、高光、运动与切镜、字幕/界面、渐变。训练/调参集和验证集按场景隔离。
- 质量比较优先使用无损 master/RAW/图序列。现有 ProRes 源可用于播放性能，若以其解码像素作质量参考，明确这是已压缩参考，不作为无损母版结论。
- 422 对照实际 10-bit ProRes 422 HQ / DNxHR HQX；444/12-bit 另建合法匹配矩阵。用探测结果核对实际 profile、pix_fmt、位深，不能只相信编码命令标签。
- 每个配置至少 5 轮交替 A/B，稳定后正式统计；报告原始逐帧样本、warmup、热状态、CPU 负载与 CI。按运行轮次/场景做配对统计，避免把相邻帧当成完全独立样本。
- 同一平台扫 1/2/4/8/16 worker，以硬件能力为界；单帧、批量、多轨单列。编码和解码可选不同最优线程数，双方比较同时给同预算及各自最佳配置。
- 记录 commit、工作树补丁哈希、实际加载库路径/SHA、构建参数、输入 SHA、完整配置、脚本版本、命令及机器信息。开发期允许 dirty，但必须可还原；正式结果使用冻结快照，不为跑基准丢弃用户修改。

| 第 2 周 | D1、D2，检查 D3 | 不改像素和位流，能拿到多少真实播放加速？ |
| 第 3 周 | D3、C0、E1 诊断 | 剩余压缩空间来自哪些符号？编码时间花在几次重复工作上？ |
| 第 4～5 周 | C1；按证据选择 C2 或 E1 完成 | 有无像素完全相同、文件更小、解码不慢的组合？没有则停止默认替换 |
| 第 6 周 | Q0 | 本机各档位和播放场景是否通过？达芬奇差距还剩多少？ |
| 第 7～8 周（条件） | ARM-D、V3-D 或剩余集成 | 仅处理已证明有价值的平台/路径缺口；重跑受影响门 |

## D3 解码 worker 预算首轮

新增 `src/shared/codec/decode_worker_budget.py` 作为进程内协作式预算登记表。`ToposMediaSource` 和 `ParallelSequentialDecoder` 在创建 context 时登记角色、请求上限和当前 slice pool 容量；多个 context 同时存在时按至少 1 worker、剩余 worker 轮询分配，并通过新的 `tc_decoder_set_max_slice_workers` 原子更新已存在 context。正在执行的帧先使用已采样的预算，下一帧采用新预算，避免重建 decoder 或改变像素语义。`diagnostics` 记录 active、assigned_total、capacity 和 oversubscribed 状态，显式显示未接入预算的路径。

基于同一 2K Topos 文件、Release、进程 pool 设为 4 的短样本，单播放 context 的 `decode_workers=0/2/4` 顺序读取分别得到 p50 约 `7.50/12.01/7.62 ms`（各 32 帧、3 轮，p95 约 `9.52/16.96/9.51 ms`），说明在本机单路场景不应把 context 限额设为 2。并行导出 2 路时，D3 基准记录峰值为 playback 2 + export 1 + 1，总分配 `4/4`，播放 p50 `10.37 ms`、p95 `14.07 ms`、p99 `14.61 ms`、约 `91 fps`；这是调度边界样本，不等同于完整 GPU 播放掉帧结论。基准入口为 `tools/bench_decode_worker_budget.py`，结果写入 `bench_out/d3_budget/`。

D3 决策：保留单路默认的共享预算（单 context 仍获得完整 pool），并发 context 自动公平收敛到总预算；不把 2-worker 限额设成默认。后续 GPU/UI trace、真实导出任务和跨平台矩阵必须沿用同一预算快照口径。

## 6. 解码提速的具体实施边界

### 6.1 现有默认 V2 与产品链：先确认已有优化在工作

已有持久线程池、worker scratch、VLC/Rice 查表、融合 scan-to-plane、AVX2 inverse/DC-only；Python 侧已有持久 decoder、plane pool、native packet-into、按预算读前、跨帧 batch、连续 pread + arena。代码入口见：

- [codec.c](../src/codec/codec.c)、[color_store.h](../src/codec/color_store.h)、[color_scan.h](../src/entropy/color_scan.h)、[decoder_ctx.c](../src/codec/decoder_ctx.c)。
- [topos_binding.py](../../../src/shared/codec/topos_binding.py)、[topos_source.py](../../../src/shared/media/topos_source.py)。

重点检查实际加载的库是否支持快路、`decode_path` 是否为预期路径、缓冲持有是否造成池耗尽，以及 present 之前的上传/转换是否才是热点。若 CPU 平面已经及时就绪，继续改 IDCT 不会解决 GPU 或队列阻塞。

保留 CRC 与边界验证。当前已有一次 slice-worker CRC，只有测出重复校验且能证明信任边界不变时才消除重复；不能直接关 CRC 换速度。所有 OpenGL 操作继续由项目渲染线程执行，不将解码阻塞或 GPU 调用移入 UI 线程。

若某函数只占帧总耗时 5%，即使完全消除，其总耗时收益也最多约 5%。每项 D2 工作先给出这个上限，再决定是否值得改动。

### 6.2 V3：明确存在的实现缺口

| 问题 | 对应代码 | 改造与约束 |
| --- | --- | --- |
| 每块独立反量化再走公共 inverse wrapper | `intra.c::reconstruct_block`、`transform.c` | x86 已可调 AVX2，不能称全部标量；复用帧入口解析好的单块融合函数，保持舍入/截断顺序完全一致 |
| 未利用已有 rowmask 和 DC-only 信息 | `intra.c`、`color_store.h` | 常量残差加预测、零残差直接重建等精确快路；仍需更新邻居边界，不可跳过依赖 |
| 每个 slice 重复申请 DC 行和重建边界 | `codec.c` 的 V3 dispatch、`intra.c::edges_init`/解码分配 | 已接入 decoder-context worker-slot grow-only 池：复用 DC 行和 top/bottom 边界；几何稳定时不再分配，尺寸增大时整体换池，失败回退到有界临时分配；继续覆盖尺寸切换、OOM、batch 和并发 |
| slice 内依赖前块重建 | 像素方向预测 | 保留 slice 级并行；不能直接搬用互不依赖的四块批量重建 |

这些是实现优化，不保证方向预测能获得足够的压缩收益。V3 完成提速后仍须与实际默认策略重新对拍。

### 6.3 明确不再作为首选的方向

既有审计已记录四块 SoA/sparse-basis IDCT、PCLMUL/多任务 CRC、小粒度大融合、packet parse 并行和盲调 VLC 的否证结果。除非平台、数据布局或热点分布出现新证据，不重新排成“确定有效”的工作。扩大读前、增加线程、GPU 解码也须先证明端到端净收益，包含启动、同步、传输、内存和 seek 成本。

## 7. 减小体积：固定重建结果，联合优化语法和解码操作数

优先固定现有默认编码器产生的**量化系数序列和辅助语义**，重新表示符号；逆变换、重建和图像保持一致。C0 输出应包含每项真实字节占比和符号数量，不能只给一个“熵更低”的平均值。

1. **先减少 token 操作数。** 检查常见 run/level 或小 level 组合是否值得联合表示。更短的码不一定更快；每块少一次查表/分支才可能同时帮助解码，需包含 escape 和稀有符号的成本。
2. **再比较熵后端。** 原型优先考察切片内多独立状态的 rANS，使用有限、可验证的表；测试表大小、状态数、上下文数和初始化成本。FSE 为备选；逐符号自适应算术编码列为对照，不因为名称更先进就默认采用。
3. **保持随机访问和有界工作量。** 表在独立解码单元内可恢复；规定状态、符号数、归一化频率、escape、尾部与截断规则。避免为了省表头引入跨帧熵状态而扩大 seek 依赖。
4. **回退也计费。** 新熵方式没收益的内容可选择已有表示，但开关、码表和容器版本限制都纳入计算。不能宣称“有 VLC fallback 就绝不会变大”；整文件最终仍须通过体积门。

参考实现用于理解多状态布局与建立实验，不将其微基准速度当成 Topos 收益：[rANS 作者实现](https://github.com/rygorous/ryg_rans)、[FSE 作者实现](https://github.com/Cyan4973/FiniteStateEntropy)。若采用外部代码，固定提交与许可证，并另行验证跨平台整数语义、字节序及异常输入。

第一轮将“验证集完整文件总字节减少至少 5%，且其余严格门通过”作为**继续投入熵大改的价值门**，不是预测收益。若只有 1%～2% 且维护复杂，可结束该方向；不能为了达到 5% 修改 QP 或色度质量。

方向预测改变了残差统计，但熵模型实验不必等待方向预测成功：先在当前默认系数上获得可验收结果；未来 V3 若成熟，单独重新训练/验证模型。暂不增加 35 模式、分块、多变换核、全搜索 RDO 或帧间预测。它们需要独立的画质、编码成本及访问延迟预算。

## 8. 编码提速：消除额外工作，保留质量与码率搜索契约

- 分开测 packed RGB/BGR 转平面、范围验证、DCT、量化/符号统计、熵输出、sized 探测和 mux；已有 cache、QP hint、统计融合不再从零实现。
- 若实际导出仍被 Python 全平面转换支配，评估在既有渲染链直接输出目标平面，或原生融合转换。必须逐像素验证舍入、range、chroma siting、下采样和 HDR 元数据；GPU 浮点结果不同就不能算严格无损优化。
- 记录每帧 sized 的 probe 数、cache hit、fallback 和超预算帧。优化可证明冗余的计算；跳过候选须有可靠下界或等价证明，不能把“附近 QP 大概率合适”当成保持最小命中 QP 的证明。
- V3 的重建邻居依赖 QP，不能复用 V2 的 source-DCT cache。当前最多 64 次完整重编码的 oracle 保留用于差分；未证明等价的快速搜索不得静默替换。
- V3 模式预筛会影响最终决策。减少候选数量属于新质量/码率实验；若与现有输出不同，不能列入本计划的严格像素一致成果。

## 10. V6 方向预测 + 自适应熵编码试验（2026-09-07）

为验证“先方向预测、再自适应熵编码”的组合，新增 V6 实验位流：保留 V3
闭环方向预测和量化决策，颜色 slice 使用模式标志的二进制范围上下文和
DC/AC 的切片内 canonical VLC/raw reservoir；Alpha、DCT、量化和切片 CRC 不变。规范见
[`bitstream_spec_v6_range.md`](bitstream_spec_v6_range.md)，原始结果见
[`intra_phase2_results.json`](intra_phase2_results.json)。V6 通过 10/12-bit、
4:2:2/4:4:4、奇数尺寸、Alpha、stride sentinel 和截断范围 coder 单元测试，
但仍作为显式实验选项，不替换默认 V2。

在同一张 1920×1080、4:2:2、10-bit 原始帧上，V6 与 V3 使用完全相同的 QP、
矩阵和预测重建，因此有效像素逐值相同；V6 只改变残差表示。第二轮将 AC 改为
`(run, level)`，并把 DC、level suffix 和 sign 放到目录声明的 raw side stream；
范围解码热路只处理模式标志。V6.1 相对 V3 的包体积变化为 low +1.2%、
medium +2.4%、high +3.7%、ultra +6.2%；同一 clean 基准的解码时间约为
V3/V6.1 `9.58/7.49`、`7.89/7.88`、`9.36/8.41`、`9.66/10.76 ms`；5 轮暖态中位数为 `8.46/7.58`、`8.73/8.07`、`7.32/7.88`、`9.57/10.69 ms`。
这次改造保留了逐值画质，并把解码成本压回 V3 的约 1.0–1.1 倍，达到当前
解码速度候选门；代价是高质量档体积暂时增加，不能直接替换默认 V2。

下一步仍是“保留 V6 预测语义，在不把高频符号放回算术热循环的前提下追回码率”：
优先评估多状态 rANS/FSE 批量表或离线码表选择，保持 slice 可独立解码、CRC 和
像素逐值不变；每个候选必须重新通过同一组码率、解码速度和异常输入门。当前
默认播放继续使用 V2/V3 快路，V6.1 保留为显式实验选项。
